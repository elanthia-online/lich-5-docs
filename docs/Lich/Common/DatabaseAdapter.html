MIN_UPDATE_ATTEMPTS =

update_settings keeps reading a row and trying to store it, while other writers keep changing it in between, for as long as a write would wait for SQLite's lock (Lich.sqlite_busy_timeout_ms), and at least this many times. A writer whose row takes longer to rebuild than its rivals' does loses more often, so a fixed count would give up on it first.

3
MAX_RETRY_PAUSE =

Longest pause, in seconds, before trying again. Each pause is random, up to 4 ms before the second attempt and doubling from there, so that competing writers drift apart.

Sets up a database adapter for persistent settings storage.

Creates or opens a SQLite database at data_dir/lich.db3 and initializes a table for the given script. Also opens a separate read-only connection for tracking database changes via PRAGMA data_version, avoiding GVL stalls when checking if other processes modified settings.

#data_version ⇒ Integer?

A number that changes whenever lich.db3 has had a commit since it was last read, or nil when that can't be told right now.

Every Lich session is a separate process, and Settings caches rows per process. SQLite's PRAGMA data_version changes when another connection commits, so a cache can compare it with the value seen when a row was read and re-read the row only when it may have changed. The pragma reports changes by other connections only, and Sequel may hand each thread a different connection, so it is read on a connection of its own that never writes: every commit, from another process or from this one, changes it.

The connection has no busy timeout. While another process holds the database's exclusive lock (a commit in progress, or a script holding it), the read fails at once and this returns nil, rather than waiting inside SQLite, which keeps the GVL and would stall every thread of this process. Callers then keep what they have; a read that overlaps a commit may see the database as it was before it. The read runs in one C call (sqlite3_exec), so no lock is held while Ruby code runs.

The pragma counts per connection, starting again from 1 on a new one, so after an error has closed the connection the reopened one could repeat a value already handed out while the database has since changed. Each connection therefore gets a range of its own: its values are offset by 240 times the number of connections opened before it. No value is handed out twice for different states of the database, and every value from a reopened connection is greater than every earlier one (a connection would need 240 commits to reach the next range).

No Ruby lock is held on the way, so a cache hit never waits for one. Ruby's Mutex is not fair: a thread calling this in a tight loop would take the lock back before a waiting thread got to run, and stall other threads' Settings reads (measured: up to seconds with the lock held around the pragma, about 100 ms now and then with it held only to record the value). The GVL already keeps two threads out of the C call at once. @version_mutex guards only opening and closing the connection; a value read on a connection that another thread has closed or replaced meanwhile is discarded (nil).

Returns:

  • (Integer, nil)

def data_version
  db = @version_db || open_version_connection
  # Read after db: a connection is published only after its offset is
  # set, and a connection replaced after this point fails the identity
  # check below.
  base = @version_base
  raw = Integer(db.execute_batch2('PRAGMA data_version').dig(0, 0))
  return nil unless @version_db.equal?(db)

  base + raw
rescue SQLite3::BusyException
  nil
rescue SQLite3::Exception, ArgumentError, TypeError => e
  if close_version_connection(db) && !@version_error_reported
    @version_error_reported = true
    Lich.log("--- Error: cannot tell whether settings changed in lich.db3 (#{e.class}: #{e.message}); settings may not show other sessions' changes ---")
  end
  nil
end

def get_settings_by_scope_prefix(script_name, scope_prefix)
  prefix = scope_prefix.to_s
  @table.where(script: script_name).select(:scope, :hash).each_with_object({}) do |row, result|
    scope = row[:scope].to_s
    next unless scope.start_with?(prefix)

    begin
      result[scope] = Marshal.load(row[:hash])
    rescue StandardError => e
      Lich.log("--- Error: skipping unreadable settings row script=#{script_name} scope=#{scope}: #{e.class}: #{e.message} ---")
    end
  end
end

def save_settings(script_name, settings, scope = ":")
  blob = serialize_settings(script_name, settings)
  return false unless blob

  begin
    statement { upsert_settings(script_name, scope, blob) }
    return true
  rescue StatementFailed => e
    report_database_error(e.cause)
  rescue => e
    Lich::Messaging.msg("error", "--- Unexpected error while saving settings ---")
    Lich.log("--- Unexpected error while saving settings ---")
    Lich.log("#{e.message}\n#{e.backtrace.join("\n")}")
  end

  false
end

#transaction(&block) ⇒ Object

Runs the block inside one SQLite write transaction (BEGIN IMMEDIATE). The write lock is taken before the first read, so a read-modify-write inside the block cannot interleave with another process's write. A nested call joins the outer transaction. If the block raises, nothing it wrote is kept. (Sequel's SQLite adapter re-raises an ArgumentError from the block as Sequel::DatabaseError.)

Raises:

  • (Sequel::DatabaseError) —

    if the database stays locked past the busy timeout.

#update_settings(script_name, scope = ":", on_stored: nil) {|fresh| ... } ⇒ Hash?

Changes one row without losing what other writers saved in the meantime.

Every Lich session is a separate process with its own settings cache, and all of them share lich.db3. Writing a cached copy of the row back erases whatever other sessions saved in between. This method reads the row as it is now, lets the block change it, and stores the result only if the row still holds exactly the bytes it read: one conditional UPDATE (or, for a new row, an INSERT that does nothing on conflict). If another writer got in first, it pauses briefly, reads the row again and calls the block again, until the busy timeout has passed (see MIN_UPDATE_ATTEMPTS).

Each statement takes and releases SQLite's write lock by itself, so the lock is never held while Ruby code (the block, Marshal) runs. Holding it there would make every other writer in this process wait out its busy timeout inside SQLite, which keeps the GVL and stalls every thread.

on_stored, when given, is called with the stored row right after the store succeeds, with Thread#kill and Thread#raise held back from the store until on_stored returns. A caller that caches the row passes its cache update here: a script killed (Script#kill) just after the row was committed still leaves its cache holding what the database holds. Only the store is covered, not the block or the pauses between attempts, so a kill waits at most for that one statement (which SQLite already runs without letting other Ruby code in).

A stored row that cannot be read (NULL, truncated, or holding a class this process does not have) is never overwritten: another session may still be able to read it. The error is reported and raised, as a read of that row (get_settings) raises it.

def update_settings(script_name, scope = ":", on_stored: nil)
  started = Process.clock_gettime(Process::CLOCK_MONOTONIC)
  budget = Lich.sqlite_busy_timeout_ms.to_f / 1000
  attempts = 0
  loop do
    sleep(rand * [0.002 * (2**[attempts, 5].min), MAX_RETRY_PAUSE].min) if attempts.positive?
    attempts += 1
    row = statement { read_row_in_one_call(script_name, scope) }
    old_blob = row && row[:hash]
    updated = yield(row.nil? ? {} : load_stored_row(script_name, scope, old_blob))
    return nil if updated.nil?

    new_blob = serialize_settings(script_name, updated)
    return nil unless new_blob

    stored = Thread.handle_interrupt(Object => :never) do
      next false unless statement { store_if_unchanged(script_name, scope, old_blob, row.nil?, new_blob) }

      on_stored&.call(updated)
      true
    end
    return updated if stored

    elapsed = Process.clock_gettime(Process::CLOCK_MONOTONIC) - started
    break if attempts >= MIN_UPDATE_ATTEMPTS && elapsed >= budget
  end

  message = "--- Error while saving settings: #{script_name} (#{scope}) kept changing, gave up after #{attempts} attempts ---"
  Lich::Messaging.msg("error", message)
  Lich.log(message)
  nil
rescue StatementFailed => e
  report_database_error(e.cause)
  nil
end

#update_settings!(script_name, scope) ⇒ Hash?

Atomically reads, changes and writes one settings row.

Yields a fresh copy of the stored hash ({} when there is no row) inside #transaction. If the block returns a Hash, that Hash is written to the row; if it returns nil, the row is left as it was.

Raises on every failure, like #save_settings!, so the caller can tell that nothing was written.

Returns:

  • (Hash, nil) —

    what the block returned

Raises:

    if the database is locked or the write fails, or if loading the stored row raises ArgumentError (truncated Marshal data, for example; Sequel re-raises an ArgumentError from the block as Sequel::DatabaseError, with the ArgumentError as cause)

  • (StandardError) —

    whatever else Marshal.load raises on a stored row that can't be loaded (usually TypeError), without yielding

  • (TypeError) —

    if the block returns something other than a Hash or nil

def update_settings!(script_name, scope)
  transaction do
    updated = yield(get_settings(script_name, scope))
    unless updated.nil? || updated.is_a?(Hash)
      raise TypeError, "update_settings! block must return a Hash or nil, got #{updated.class}"
    end

    save_settings!(script_name, updated, scope) if updated
    updated
  end
