Overview

Lock waits that let the rest of the process keep running.

sqlite3's busy_timeout waits inside C with the GVL held. If the lock holder is another thread of this process that still has Ruby code to run before it commits, it can't run, and the waiter fails when the timeout expires. A waiting thread also freezes every other thread (game I/O included) while another process holds the lock. Every connection Lich opens to lich.db3 (the Sequel pool, Lich.db, the session summary connection) gets the Ruby handler: a thread spinning in C with the GVL held while another thread of this process sleeps in the Ruby handler holding the lock it waits for would stall both for the full timeout.

A busy handler written in Ruby sleeps between retries, which releases the GVL. SQLite calls it from inside the C call that is waiting for the lock, though, so a Thread#kill, Thread#raise or Timeout delivered during that sleep would unwind through SQLite's C frames and leave the connection's mutex locked; the next thread to use that connection would then block forever with the GVL held. On these connections every sqlite3 entry point that can wait for a lock therefore defers interrupts until SQLite returns:

  • SQLite3::Statement#initialize (sqlite3_prepare) and #step (sqlite3_step), which carry #execute, #query, #prepare, #execute_batch, #transaction and everything Sequel sends;
  • Database#exec_batch (sqlite3_exec), which carries #execute_batch2;
  • SQLite3::Backup#step (sqlite3_backup_step), when either end of the backup is one of these connections (see SQLiteBusyWait::Backup).

An interrupt that arrives during a lock wait ends the wait: the handler gives up at its next poll (within about 1 ms), SQLite returns SQLITE_BUSY, and the interrupt is delivered as the call returns, in place of the BusyException. The interrupted statement does not run. Letting the wait go on until the lock freed would deliver the interrupt after the write had landed: a Timeout around the write reports a failure for a write that happened, a second interrupt can arrive meanwhile and land outside the scope it was meant for (a Timeout::ExitException after its Timeout block has returned), and a killed script's write can land after the writes its cleanup makes once the kill returns. With the C busy timeout none of this could happen, because nothing else ran until the wait ended.

Two exceptions keep waiting until the lock frees or the busy timeout expires, and deliver the interrupt afterwards:

  • a call that starts with an interrupt already pending, which means the caller deferred it with Thread.handle_interrupt to finish its writes first (see SQLiteBusyWait.wait_uninterrupted);
  • ROLLBACK (see SQLiteBusyWait::Transactions).

A caller that defers interrupts itself and is interrupted during the wait gets the BusyException; the interrupt stays deferred, as it asked.

While one thread sleeps in the handler, SQLite holds that connection's mutex and other threads run, garbage collection included. GC finalizes an unclosed SQLite3::Statement with sqlite3_finalize, which needs the same mutex and waits for it with the GVL held: the sleeping thread can never wake and the process freezes. So every open statement on these connections is kept referenced by its connection until it is closed (see SQLiteBusyWait::Statement); GC never finalizes one while it is open. A statement nobody closes is freed with its connection.

A connection that several threads share has one more hazard: a second thread calling into it while the first sleeps in the handler blocks on the same connection mutex with the GVL held. Shared connections are therefore serialized; see SQLiteBusyWait::SerializedDatabase.

Deferring interrupts moves where a Thread#kill lands inside Sequel::Database#transaction to the end of BEGIN or COMMIT; see SQLiteBusyWait::Transactions.

def self.install(conn, timeout_ms, shared: false)
  return conn unless conn.respond_to?(:busy_handler)

  prepare_sqlite3
  timeout_s = timeout_ms / 1000.0
  deadline = nil
  conn.busy_handler do |count|
    next false if give_up_for_interrupt?

    now = Process.clock_gettime(Process::CLOCK_MONOTONIC)
    deadline = now + timeout_s if count.zero? || deadline.nil?
    next false if now > deadline

    unless count.zero?
      sleep(POLL_INTERVAL_S)
      # An interrupt that arrived during the sleep woke it. Check again
      # before SQLite retries: the retry runs in C with the GVL held, so
      # once this check passes no other thread can interrupt before it,
      # and a write that lands was never interrupted.
      next false if give_up_for_interrupt?
    end
    true
  end
  conn.extend(Connection)
  conn.extend(SerializedDatabase) if shared
  conn
end

def self.keep_waiting_through_interrupts
  thread = Thread.current
  outer = thread.thread_variable_get(KEEP_WAITING_KEY)
  thread.thread_variable_set(KEEP_WAITING_KEY, true)
  begin
    yield
  ensure
    thread.thread_variable_set(KEEP_WAITING_KEY, outer)
  end
end

def self.prepare_sqlite3
  SETUP_LOCK.synchronize do
    return if @sqlite3_prepared

    serialize_c_methods(SerializedDatabase, ::SQLite3::Database, UNSERIALIZED_DATABASE_METHODS)
    serialize_c_methods(SerializedStatement, ::SQLite3::Statement, UNSERIALIZED_STATEMENT_METHODS)
    ::SQLite3::Statement.prepend(Statement) unless ::SQLite3::Statement <= Statement
    # SQLite3::Backup exists only when sqlite3 was built with the backup API.
    ::SQLite3::Backup.prepend(Backup) if defined?(::SQLite3::Backup) && !(::SQLite3::Backup <= Backup)
    @sqlite3_prepared = true
  end
end

Runs one sqlite3 call that may wait for a lock with interrupts deferred. An interrupt already pending here was deferred by the caller (otherwise it would have been delivered before this call), so the caller wants its writes finished first: the busy handler keeps waiting for this call. def self.wait_uninterrupted
  Thread.handle_interrupt(Object => :never) do
    next yield unless Thread.pending_interrupt?

    keep_waiting_through_interrupts { yield }
  end
end
